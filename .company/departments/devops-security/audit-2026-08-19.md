## Verification of the 3 Documented Findings (`docs/07-roadmap.md`) -- All Three Now Resolved

1. **"Unauthenticated wallet-pass-download endpoint" -- FIXED.** Both `app/api/wallet/apple/[passId]/route.ts` and `app/api/wallet/google/[passId]/route.ts` require a `token` query param matched against `row.apple_auth_token` / `row.google_auth_token` respectively, returning 401 on mismatch, before any pass data is generated or returned.
2. **"Non-durable rate limiting" -- FIXED.** `lib/rate-limit.ts` is Postgres-backed (`supabase` RPC `check_rate_limit`, migration 004) rather than an in-process `Map`, so it's now consistent across serverless instances. Note: it **fails open** on DB error (documented in the file's own comment as an intentional defense-in-depth tradeoff, not the primary double-award guard) -- worth Dev/DevOps confirming that's still the desired behavior as the app nears launch, since fail-open under sustained DB errors means no rate limiting at all during an outage.
3. **"Hardcoded dashboard branding" -- FIXED.** `app/[locale]/dashboard/settings/branding/page.tsx` is a real session-gated settings page backed by `components/dashboard/settings/branding-form.tsx`, not hardcoded values.

## Update -- 2026-08-19: Rate Limiter Fail-Open Investigation

Reviewed both call sites of `checkRateLimit` (`lib/rate-limit.ts`) and the underlying Postgres function (`supabase/migrations/004_hardening.sql`):

1. **`/api/scan/route.ts`** (merchant/staff-only, authenticated via `requireCapability("scan")`). Fail-open here is low-risk: the actual scan/award write goes through `record_scan_event`, an atomic RPC that re-verifies ownership/active-state and computes progress **inside a single locked transaction** (`supabase/migrations/019_atomic_scan_events.sql`). That RPC -- not the rate limiter -- is the real guard against double-award, exactly as the code comment in `lib/rate-limit.ts` states. If rate limiting fails open here, worst case is a staff member can scan faster than intended during a DB blip; correctness is unaffected.

2. **`/api/customers/enroll/route.ts`** (public, unauthenticated, keyed only by `x-forwarded-for` IP). This is the higher-risk case: it's the **only** throttle on a public endpoint that does real work per request (DB writes, Apple/Google Wallet pass generation -- actual compute/API cost). If the rate limiter fails open during exactly the kind of DB stress that would trigger it, there's no other guard against a flood of enrollment requests (dedup only merges rows that share a phone/email; anonymous submissions still create new rows and still trigger wallet generation).

**Conclusion: the fail-open design is intentional and correctly reasoned for the case it was written for** (protecting the scan/award path from a rate-limiter outage without risking double-award, which is independently guarded). **It is not yet differentiated for the enroll endpoint**, where fail-open removes the only abuse guard on a costly public surface at the worst possible time. Given the "no external funding, keep costs lean" constraint (`.company/STATE.md`), this is worth a decision before launch:
- Option A: leave as-is (accept the risk -- DB outages should be rare, and this is a narrow window)
- Option B: make `/api/customers/enroll` fail **closed** specifically (reject on rate-limiter DB error), since it's public/unauthenticated and cost-incurring, while leaving `/api/scan` fail-open (authenticated, correctness-guarded elsewhere)
- Option C: add a cheap complementary guard in front (e.g. Vercel/Cloudflare edge-level rate limiting) so the Postgres check isn't the only line of defense

No code changed for this item -- it's a design tradeoff, not a bug, so it goes to the CEO rather than being auto-fixed.

## Update -- 2026-08-19: CEO Decisions Applied

**1. Rate limiter: Option B implemented.** `lib/rate-limit.ts`'s `checkRateLimit` now takes an optional `{ failOpen?: boolean }` (default `true`, preserving existing behavior everywhere it wasn't explicitly changed). `app/api/customers/enroll/route.ts` now passes `{ failOpen: false }` -- a rate-limiter DB error on enroll now blocks the request (503-via-429-path... actually returns the same 429 `rate_limited` response) instead of allowing it through. `app/api/scan/route.ts` is unchanged (still fails open, correctness guarded by the atomic `record_scan_event` RPC). Verified: `npm test` (43/43 passing) and `npm run build` (clean) after the change.

**2. `sharp@0.35.3` upgrade: investigated, not applied.** Findings:
- **Breaking change that matters**: sharp 0.35.0 drops Node 18 support, now requires **Node >= 20.9.0**. This repo's `Dockerfile` uses `node:22-alpine` (fine). Vercel's runtime Node version isn't pinned anywhere in this repo (`vercel.json` has no `engines`/runtime override) -- Vercel deprecated Node 18 project-wide well before now, so production is almost certainly already >=20, but this should be confirmed directly in the Vercel project's Node.js Version setting before upgrading, since it's not verifiable from the repo alone.
- Other 0.35.0 breaking changes (`failOnError` constructor option removed, `format.jp2k` renamed to `format.jp2`, `install` script removed) -- **none apply**: `git grep` confirms this codebase doesn't use any of them.
- **Functional smoke test**: installed `sharp@0.35.3` locally (`--no-save`, not persisted) and exercised every sharp API `lib/wallet/heroImage.ts` actually calls -- `resize`, `extract`, `metadata`, `jpeg({quality})`, `png()`, `fit: "inside"`, `fit: "cover"` -- all produced correct output. Reinstalled `sharp@0.34.5` afterward to restore the approved state; confirmed via `npm audit` (back to 3 vulnerabilities: joi, passkit-generator, sharp) and `package.json`/`package-lock.json` diff (only the previously-approved `next`/`eslint-config-next` changes remain).
- **Not verified from the repo**: whether the Alpine/musl prebuilt binary for `sharp@0.35.3` installs cleanly inside this project's actual `Dockerfile` build (only checked local Windows install + Node version compatibility) -- if the Docker path is actually used in production, run `docker build` with the bumped version before shipping, not just `npm install` on a dev machine.

**Recommendation**: low risk to upgrade once the Vercel Node runtime version is confirmed >= 20.9.0 -- no code changes needed, no APIs in use are affected, and the exact call patterns used in production were smoke-tested successfully. Still awaiting CEO go-ahead to actually apply it.
